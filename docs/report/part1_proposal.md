> 표지(프로젝트명·개발기간·참여자 연락처 표)는 중간 보고서 원본 양식을 그대로 사용한다. 연락처 등 개인정보는 이 초안 파일에 싣지 않는다.
> 작성 기준: 2026-09 현재 구현 코드(Kotlin + Jetpack Compose, d:\gemma4).

## 1. 시스템 개요

### (1) 시스템 이름

본 시스템의 명칭은 '온디바이스-클라우드 하이브리드 LLM에 자율 검증 하네스를 적용한 지능형 모임 조율 에이전트'이며, 앱 서비스명은 '모이미(모임 AI 비서)'이다.

### (2) 시스템 개요

본 시스템은 다자간 모임 조율 과정에서 발생하는 의사소통 비용과 정보 파편화 문제를 해결하는 Android 기반 지능형 에이전트 앱이다. 단순 문답형 챗봇의 한계를 넘기 위해, 기기 내부 연산과 클라우드 연산의 역할을 분리한 하이브리드(Two-Track) LLM 아키텍처를 채택하였다.

- **트랙 1 — 백그라운드(프라이버시 및 상태 압축, 온디바이스)**: 채팅방에 메시지가 10개 쌓일 때마다 온디바이스 LLM인 Gemma 4 E2B(LiteRT-LM, GPU 백엔드)가 최근 대화를 분석하여 참석자·선호/불호·가능 일정만을 구조화된 JSON으로 압축한다. 출력은 툴 스키마 기반 제약 디코딩(constrained decoding)으로 문법이 강제되어 깨진 JSON이 구조적으로 발생하지 않으며, 직전 상태와 결정론적으로 병합되어 Room DB(`user_status`)에 갱신(Upsert)된다. 채팅 원문은 이 과정에서 기기 밖으로 나가지 않는다.
- **트랙 2 — 포그라운드(통제 및 추론, 하이브리드)**: 사용자가 '이야기 정리'를 요청하면 Gemma 4가 채팅 원문을 익명화 요약하고, 결정론적 PII 스크러버(`PiiScrubber`)가 전송 직전 이름·연락처·이메일을 최종 마스킹한다. 이 요약문과 성향 프로필, 온디바이스 시맨틱 검색(EmbeddingGemma-300m)으로 회수한 과거 후기만이 클라우드 LLM(Gemini)에 전달된다. 중앙 오케스트레이터(`AgentOrchestrator`)는 Gemini의 Function Calling(날씨 조회 `getWeather`, 장소 검색 `searchPlace`)을 대리 실행하고, 도출된 추천을 자율 검증 하네스 — Guardrail(장소 실존 팩트 체크)과 Reflection(사용자 불호 제약 위반 자기비평) — 로 검증한다. 검증 실패 시 반려 사유를 프롬프트에 누적하여 최대 3회 자가 수정(Self-correction)을 반복한다.
- **클라우드 경계**: Gemini·카카오 로컬·기상청 API 키는 앱에 존재하지 않는다. 앱은 Firebase Cloud Functions의 callable 프록시(로그인 사용자 전용)를 통해서만 외부 API에 접근하며, 프록시는 키를 붙여 전달하는 역할만 수행한다.

### (3) 시스템 특성 및 차별성

본 시스템은 기존 캘린더/지도 앱의 수동성과 범용 LLM 챗봇의 신뢰성 한계를 '하네스 엔지니어링'으로 구조적으로 극복한다.

- **2중 게이트 프라이버시 방화벽(온디바이스 AI + 결정론적 스크러버)**
  기존 일정 관리 챗봇은 맥락 파악을 위해 사담과 개인정보가 섞인 채팅 원문을 통째로 클라우드에 전송해야 했다. 본 시스템은 Gemma 4가 기기 내부에서 익명화 요약을 생성하고, 그 결과를 다시 규칙 기반 `PiiScrubber`(참가자 명단 대조·전화·이메일 정규식·호칭 백스톱)가 검사한다. "이름을 언급하지 말라"는 프롬프트 지시는 1차 방어일 뿐이며, 집행은 결정론적 게이트가 담당한다. 클라우드로 나가는 모든 자유 텍스트(요약문·후기)가 이 게이트를 통과한다.

- **압축된 상태 관리와 온디바이스 시맨틱 RAG를 통한 장기 기억**
  대화 원문을 누적하는 기존 RAG는 대화가 길어질수록 컨텍스트가 소실되고 토큰 비용이 증가한다. 본 시스템은 성향을 JSON으로 압축해 Room DB에 증분 병합하고(리스트당 최대 25건 상한), 모임 후기는 EmbeddingGemma-300m(768차원)으로 기기 안에서 임베딩·검색한다. 후기 검색은 방 단위가 아니라 사용자 단위로 동작하여 지난 모임의 취향이 새 톡방 추천에도 누적 반영되며, 후기조차 기기 밖으로 나가지 않는다.

- **에이전트 주도적 도구 활용(Function Calling)**
  외부 API를 정해진 순서로 호출해 텍스트로 주입하던 단방향 파이프라인과 달리, Gemini는 모임 상황을 판단해 스스로 `getWeather`·`searchPlace` 도구 실행을 오케스트레이터에 요청한다. 오케스트레이터는 다중 도구 호출을 병렬로 대리 실행하고 결과를 모델에 되돌려 재추론시키며, 도구 왕복은 상한(8회)으로 제한된다.

- **2단 자율 검증 하네스를 통한 할루시네이션 차단(fail-open 금지)**
  일반 LLM은 폐업한 장소를 추천해도 그대로 노출한다. 본 시스템은 추천 장소를 카카오 로컬 API로 팩트 체크하되, 검증 결과를 OPEN/CLOSED/UNKNOWN 3-상태로 구분하여 '검증하지 못한 것'을 '검증됨'으로 위장하지 않는다(하드 게이트). 더불어 Reflection 계층이 추천 항목이 사용자의 명시 불호("싫어요:") 제약을 위반하는지 결정론적으로 자기비평한다(소프트 게이트). 실패 시 사용자 개입 없이 반려 사유를 주입해 재시도하고, 장소가 유효한 결과는 소프트 제약만 미충족이어도 최선의 결과로 보존한다.

- **참석자 조건 종합 기반의 통합 조율 자동화**
  메신저·지도·캘린더를 오가며 수동으로 취합하던 조율 과정을 대신하여, 에이전트가 성향 프로필·과거 후기·날씨·장소 검색 결과를 종합해 장소 2~3곳, 활동 2~3가지, 준비물 3~5가지를 구조화된 카드로 제시하고, 확정 일정을 인앱 캘린더에 등록한다.

## 2. 시스템 배경 및 목표 (Why)

### (1) 현황 및 문제점 (AS-IS)

**현행 비즈니스 상황**
다자간 모임 조율은 메신저(카카오톡 등), 지도(카카오맵/네이버 지도), 캘린더(구글 캘린더 등) 등 파편화된 애플리케이션을 횡단하며 이루어진다. 참석자의 일정·위치·취향을 조율하기 위한 의사소통 비용이 과도하며, 이를 해결하려는 LLM 챗봇 서비스들은 단순 문답 수준에 머물러 복잡한 조율 로직을 대체하지 못한다.

**기존 유사 시스템 비교**
- 기존 일정 관리 시스템: 사용자가 날짜·장소·참석자를 직접 취합해 입력하는 수동형 시스템으로, 조율 과정의 피로도를 해결하지 못한다.
- 범용 LLM 챗봇(ChatGPT 등): 맥락을 이해하고 장소를 추천할 수 있으나, 일회성 응답 구조라 스스로 도구를 사용하거나 결과를 검증하지 못하며, 대화 원문을 서버로 보내야 한다.

**현행 시스템의 문제점**
1. **프라이버시 침해 및 보안 취약성**: 대화 맥락 파악을 위해 사담과 개인정보가 섞인 채팅 원문 전체를 클라우드로 전송해야 한다.
2. **할루시네이션 무방비 노출**: 비결정론적 LLM이 폐업한 식당이나 존재하지 않는 날짜를 추천해도 시스템이 검증하지 못한 채 사용자에게 노출한다.
3. **토큰 낭비 및 장기 기억 유실**: 대화가 누적될수록 컨텍스트 윈도우가 폭발해 비용이 증가하고, 과거 대화의 취향 정보가 검색 과정에서 누락되거나 충돌한다.

### (2) 개발 목적 및 목표 (TO-BE)

**시스템의 목적**
온디바이스와 클라우드를 결합한 하이브리드 LLM 아키텍처와, 자율적인 오류 수정이 가능한 검증 하네스를 융합하여, 프라이버시를 보호하면서도 할루시네이션 오류가 없는 지능형 모임 조율 에이전트를 개발한다.

**시스템의 목표**
1. **온디바이스 데이터 압축 파이프라인 구축**: Gemma 4 E2B로 채팅에서 참석자 선호도·제약 조건만 JSON으로 추출하고, 제약 디코딩과 방어적 파싱으로 출력 신뢰성을 확보하며, 원문은 기기 밖으로 내보내지 않는다.
2. **구조화된 메모리 갱신 및 온디바이스 시맨틱 RAG 구축**: 추출된 상태를 Room DB에 증분 병합하고, 모임 후기를 EmbeddingGemma로 기기 안에서 임베딩·검색하여 최소 토큰으로 장기 기억을 유지한다.
3. **오케스트레이터 및 Function Calling 연동**: 클라우드 LLM(Gemini)이 기상청·카카오 로컬 도구를 스스로 호출하도록 에이전트 통제 계층을 설계하고, API 키를 앱에서 제거한 서버 프록시 경계를 구축한다.
4. **Guardrail·Reflection 기반 자가 수정 루프 구현**: 추천 결과를 외부 API 팩트 체크와 사용자 제약 자기비평으로 검증하고, 실패 시 반려 사유를 주입해 재시도하는 검증 루프를 완성한다.

### (3) 기대효과 및 활용 방안

**기술적 기대효과**
- 무거운 텍스트 연산(요약·압축·임베딩)을 엣지 디바이스로 분산하여 클라우드 호출 토큰과 비용을 절감한다.
- 검증 하네스를 시스템 레벨에 내재화하여 할루시네이션을 차단한다. 실기기 실증에서 Reflection이 사용자 불호 위반을 검출하고 3회 자가 수정으로 수렴(위반 2→2→0)하였다.
- 온디바이스 모델의 정확도를 골든 테스트로 보증한다. EmbeddingGemma 온디바이스 임베딩은 Python sentence-transformers 기준 벡터 대비 코사인 유사도 최소 0.9507(임계 0.93), 쿼리별 상위 1위 일치 5/5를 기록하였다.
- 제약 디코딩 도입으로 성향 압축의 깨진 JSON 발생이 0건이 되었다.

**사용자 기대효과**
- 사적인 대화 원문과 후기가 외부로 유출되지 않는 프라이버시 보장을 받는다.
- 별도의 프로필을 설정하지 않아도 일상 채팅에서 취향이 자동 학습되어 제로 에포트(Zero-effort) 초개인화 추천을 제공받는다.
- 추천 장소의 검증 상태(검증됨/미검증)가 정직하게 표시되어 결과를 신뢰할 수 있다.

## 3. 시스템 주요 기능 (What)

### (1) 기능 개요

본 시스템은 사용자 및 모임 관리, 온디바이스 AI 데이터 정제, 하이브리드 에이전트 및 검증 하네스, 캘린더 및 모임 아카이빙의 4대 서브시스템으로 구성된다. 핵심인 하이브리드 LLM 에이전트는 온디바이스 Gemma 4가 대화를 정제해 구조화된 장기 기억으로 압축하고, 오케스트레이터의 통제하에 클라우드 Gemini가 외부 도구(기상청·카카오 로컬)를 능동적으로 호출하여 검증된 모임 추천을 산출하는 지능형 파이프라인이다.

## 4. 시스템 사용 대상 및 사용자 그룹 (Who)

### (1) 핵심 타겟층

1차 타겟은 다자간 모임 조율 과정의 커뮤니케이션 비용(일정 취합, 장소 검색, 동선 계산)에 피로도를 느끼는 2030 세대 및 소셜 그룹(동아리, 스터디, 가족 모임 등)이다. 특히 자신의 사적인 대화가 기업 서버에 수집·학습되는 것을 꺼리는 프라이버시 민감형 사용자에게 최적화된 대안을 제공한다.

### (2) 세부 사용자 페르소나 및 해결 가치

- **그룹 A: 모임 주최자(The Organizer)**
  고충: 단톡방에서 가능한 날짜를 취합하고, 각자의 식성과 위치를 고려해 장소를 검색한 뒤 공유까지 도맡아야 하는 조율의 피로도가 높다.
  해결 가치: 오케스트레이터가 Room DB의 참석자 성향 프로필과 과거 후기를 종합해 단일화된 추천안을 도출한다. Guardrail·Reflection 루프를 통해 존재하지 않는 장소나 불호 위반이 걸러진 결과만 제시되어 주최자의 수동 개입이 줄어든다.

- **그룹 B: 수동적/조건부 참여자(Passive / Constrained Participant)**
  고충: "수요일 저녁 7시 이후만 가능하고 매운 음식은 못 먹어"처럼 뚜렷한 제약이 있지만 매번 어필하기 번거로워 수동적으로 끌려간다.
  해결 가치: 온디바이스 Gemma 4가 일상 대화에서 지나가듯 언급된 취향과 일정 제약을 백그라운드에서 포착해 영구적으로 병합·기억한다. 명시적으로 요구하지 않아도 Reflection 계층이 해당 사용자의 불호를 검증 기준에 포함시킨다.

- **그룹 C: 프라이버시 중시형 사용자(Privacy Seeker)**
  고충: AI 비서의 편의는 알지만 지극히 개인적인 대화가 외부 AI 서버로 넘어가는 것에 강한 거부감을 가진다.
  해결 가치: 민감한 사담이 섞인 원문은 기기 내부에서만 처리된다. 클라우드로는 Gemma 익명화 요약을 `PiiScrubber`가 한 번 더 마스킹한 텍스트와 비식별 성향 프로필만 전송되며, 모임 후기조차 기기 안에서만 임베딩·검색된다.

### (3) 시스템 적용 도메인 확장성

'구조화된 메모리 압축'과 '오케스트레이터 기반 자율 검증' 아키텍처는 B2C 소셜 모임을 넘어 다양한 B2B 도메인으로 확장 가능하다.
- **1단계(B2C 일상 스케줄링)**: 친구·지인 기반 사적 모임, 데이트 코스 추천, 여행 일정 기획.
- **2단계(B2B 업무 협업 툴 연동)**: 사내 메신저에 플러그인 형태로 이식하여 참석자 업무 캘린더의 공통 가용 시간을 찾고 회의실을 자동 예약하는 사내 미팅 조율 에이전트. 온디바이스 정제 계층은 사내 대화가 외부 LLM으로 유출되지 않게 하는 컴플라이언스 장치로 동작한다.

## 5. 시스템 운영 환경 (Where)

### (1) 시스템 운영 방식

본 시스템은 온디바이스-클라우드 하이브리드 아키텍처를 기반으로, 데이터 보안과 처리 효율을 위해 연산 부하를 분산하는 다계층 운영 방식을 채택한다.

**Client-Side (On-device Edge)**
- Android 14 이상, GPU 위임을 지원하는 스마트폰에서 동작하는 Kotlin + Jetpack Compose 네이티브 앱이다.
- Gemma 4 E2B(LiteRT-LM, GPU)가 성향 압축·익명화 요약을, EmbeddingGemma-300m(LiteRT)이 후기 임베딩·검색을 기기 안에서 수행한다. 두 엔진은 Mutex로 직렬화되고 임베더는 작업 단위로 로드·해제되어 메모리 경합을 방지한다.
- 성향 프로필, 모임 후기와 벡터, AI 추천 결과는 Room DB(`moim_database`)에 로컬 영구 저장된다. 채팅 원문 정제는 네트워크 없이 실시간으로 수행된다.

**Server-Side (Cloud)**
- Firebase Authentication(Google 로그인), Cloud Firestore(방·메시지·초대코드·읽음 시각 실시간 동기화), Cloud Messaging(푸시)을 사용한다. Firestore 보안 규칙으로 방 참여자만 해당 방의 메시지를 읽고 쓰며 발신자 위조를 차단한다.
- Cloud Functions(2세대, asia-northeast3)가 새 메시지 푸시 발송 트리거와 외부 API 프록시(`geminiGenerate`, `kakaoSearch`, `weatherMidFcst`)를 담당한다. 외부 API 키는 Secret Manager에만 존재하며, 프록시는 로그인 사용자의 요청에 키를 붙여 Gemini·카카오 로컬·기상청에 전달한다.
- 하네스 검증·재시도 로직은 서버가 아니라 앱의 오케스트레이터가 수행하므로, 서버는 프롬프트나 대화 내용을 저장하지 않는다.

**데이터 마이그레이션 및 상호운용성**
- 사용자 성향·후기·추천 결과는 앱 전용 로컬 DB에 저장되며 기기 간 동기화하지 않는다(프라이버시 원칙). 채팅·방 데이터는 Firestore에 있어 재설치·기기 변경 후에도 유지된다.
- 캘린더 일정은 현재 앱 메모리 상태로 관리되며 Room 영속화와 외부 캘린더 내보내기(Export)는 후속 과제이다.

## 6. 시스템 개발 관련 기술 (How)

### (1) 시스템 운영 개념 및 핵심 기술 (SOC)

**하이브리드 LLM 아키텍처 (On-device + Cloud)**
- 내용 및 필요성: 단일 클라우드 LLM 의존 시 발생하는 개인정보 유출과 토큰 비용 문제를 해결한다.
- 적용 방법: 일상 대화 분석·상태 압축·익명화 요약은 기기 내 경량 모델 Gemma 4 E2B(.litertlm, 약 2.5GB)가, 추론과 외부 도구 호출은 클라우드 모델 Gemini(gemini-3.5-flash)가 담당한다. 온디바이스 LLM은 `OnDeviceLlmPort` 인터페이스 뒤에 두어 실제 구현과 Mock 구현을 런타임에 교체할 수 있다.

**에이전트 오케스트레이션 및 하네스 (Agent Orchestration & Harness)**
- 내용 및 필요성: AI가 질문에 답하는 데 그치지 않고, 도구를 사용하고 결과를 검증하며 목표를 달성할 때까지 반복하도록 만드는 제어 기술이다.
- 적용 방법: `AgentOrchestrator`가 UI와 AI 사이의 중앙 통제실로서 프롬프트 조립, 도구 대리 실행, Guardrail·Reflection 검증, 재시도(`MAX_ATTEMPTS` = 3, 도구 왕복 `MAX_TOOL_ROUNDS` = 8)를 관리한다. 모든 루프는 명명 상수로 상한을 두어 무한 반복을 금지하며, 주요 단계는 `AgentEvent`로 발행되어 진행 화면에서 관찰 가능하다.

**LLM 함수 호출 (Function Calling)**
- 내용 및 필요성: 언어 모델이 실시간 사실(날씨, 장소)에 접근하기 위해 외부 시스템을 능동적으로 사용하도록 권한을 부여한다.
- 적용 방법: Gemini generateContent 요청에 `getWeather`·`searchPlace` 함수 명세(JSON Schema)와 응답 스키마를 주입하고, 모델이 함수 실행을 요청하면 앱이 서버 프록시를 통해 대리 호출한 결과를 함수 응답으로 되돌린다.

### (2) 기술적/이론적 기법 및 모델 적용 방안

**제약 디코딩 기반 상태 압축 및 결정론적 병합**
- Gemma 4의 압축 출력을 `record_status` 툴의 JSON 스키마로 문법 제약(LiteRT-LM constrained decoding)하여 깨진 JSON을 원천 차단한다. 툴 호출이 나오지 않으면 자유텍스트 프롬프트로 폴백하고, 정규식 블록 추출과 trailing comma 정제로 방어적 파싱한다. 추출 결과는 LLM 재요약에 의존하지 않고 직전 상태와 합집합·중복 제거로 병합해 과거 성향을 보존한다.

**결정론적 PII 스크러버**
- 순수 Kotlin 규칙 엔진이 이메일·전화 정규식, 참가자 명단 대조(3자 한국어 이름의 이름 부분 포함, 조사 처리), 호칭(님·씨) 백스톱으로 마스킹한다. JVM 단위 테스트로 검증되며, 클라우드 경계를 넘는 모든 자유 텍스트에 적용된다.

**온디바이스 시맨틱 RAG (EmbeddingGemma)**
- 후기 저장 시 문서 프리픽스("title: none | text: ")로, 검색 시 쿼리 프리픽스("task: search result | query: ")로 임베딩하는 비대칭 프리픽스를 API 수준에서 강제한다. 검색은 사용자 전체 후기에 대한 brute-force 코사인 top-k이며, Python 기준 벡터와의 골든 테스트(임계 0.93)와 랭킹 일치 테스트로 정확도를 회귀 검증한다. 임베딩 모델이 없으면 키워드(Jaccard) 폴백 리트리버로 교체된다.

**Guardrail·Reflection 자가 수정 알고리즘**
- Guardrail은 추천 장소명을 카카오 로컬 API로 조회해 OPEN/CLOSED/UNKNOWN을 판정한다. CLOSED만 재시도 사유가 되고 UNKNOWN은 통과시키되 UI에 '미검증'으로 정직하게 표기한다(fail-open 금지). Reflection은 프로필의 "싫어요:" 항목을 내용 토큰으로 분해해 한 추천 항목(장소명+이유, 활동) 안에 모든 토큰이 동시에 나타날 때만 위반으로 판정하는 정밀도 우선 매칭을 사용한다. 두 계층의 반려 사유를 합쳐 프롬프트에 누적 주입하고 최대 3회 재시도한다.

**서버 프록시를 통한 API 키 격리**
- 앱에는 외부 API 키가 없다. Cloud Functions callable 프록시가 Firebase Auth 인증을 강제하고, Gemini 모델명 allowlist·본문 크기 상한·입력 검증·업스트림 타임아웃·일시 오류(429/503) 지수 백오프 재시도를 서버 한 곳에서 집행한다.
