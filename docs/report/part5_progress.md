## 3. 프로젝트 개요

### 1) 프로젝트 목적

다자간 모임 조율은 메신저·지도·캘린더를 오가며 일정·장소·취향을 사람이 직접 취합하는 일이다. 이를 LLM 챗봇에 맡기면 채팅 원문을 통째로 클라우드에 보내야 하고, 모델이 폐업한 가게나 불호 장소를 추천해도 걸러지지 않는다. 본 프로젝트는 기존 모델(Gemma 4, EmbeddingGemma, Gemini)을 개발하는 것이 아니라, 그 모델들을 잇는 **응용 시스템**을 개발한다. 목적은 세 가지다.

1. 채팅 원문이 기기 밖으로 나가지 않는 프라이버시 구조(온디바이스 익명화 요약 + 결정론적 PII 마스킹)
2. 대화에서 성향·일정을 구조화해 누적하고, 과거 후기를 기기 안에서 의미 검색해 추천에 반영하는 장기 기억
3. 클라우드 LLM의 도구 호출(날씨·장소 검색)을 대리 실행하고, 추천 결과를 실존 검증(Guardrail)과 불호 검사(Reflection)로 검증한 뒤 실패 시 스스로 재시도하는 하네스

서비스 특성: 사용자는 별도 프로필을 입력하지 않아도 일상 채팅에서 취향이 자동 누적되고, 추천 장소에는 검증 상태(검증됨/미검증)가 정직하게 표기된다. 요약·압축·임베딩은 오프라인에서 동작하며 클라우드 호출은 추천 시점의 요약문·프로필·후기만으로 이루어진다.

### 3) 주요 이해관계자 및 타겟 대상

- **핵심 타겟**: 카카오톡 단체방으로 모임을 잡는 20~30대 친구·동아리·직장 소모임. 일정과 취향이 여러 사람에게 흩어져 있어 조율 비용이 큰 집단.
- **세부 페르소나**: (A) 총무 역할을 떠맡은 사람 — 취합·예약 부담 해소, (B) 의견을 잘 안 내는 참여자 — 채팅에서 드러난 불호가 자동 반영, (C) 프라이버시에 민감한 사용자 — 원문 비전송 구조.
- **이해관계자**: 지도교수·평가위원(캡스톤 산출물), 장소·날씨 데이터 제공자(카카오 로컬, 기상청 API 약관), Google Play(출시 정책·데이터 안전 섹션).

### 4) 운영 환경

- **클라이언트(Android 14 이상)**: Kotlin + Jetpack Compose 앱. 온디바이스 모델 2종(Gemma 4 E2B .litertlm 약 2.5GB, EmbeddingGemma .tflite 약 180MB)을 앱 전용 저장소에 다운로드해 GPU 위임으로 추론. 로컬 DB는 Room.
- **서버(Cloud)**: Firebase Auth·Firestore(채팅)·FCM(푸시)·Cloud Functions(asia-northeast3). Functions가 Gemini·카카오 로컬·기상청 API 키를 Secret Manager에 보관하고 프록시로 중계.
- **네트워크**: 추천·장소 검증·날씨 조회는 온라인·로그인 필요. 요약·압축·후기 검색은 오프라인 동작.

### 2) 기술적 문제

- **LiteRT-LM에 임베딩 API가 없음**: 생성 전용 런타임이라 EmbeddingGemma를 raw LiteRT 인터프리터 + DJL 토크나이저로 별도 구동. 두 네이티브 런타임의 공존을 스파이크로 먼저 검증한 뒤 채택했다.
- **EmbeddingGemma 공식 저장소가 gated**: 라이선스 동의·토큰 필요. 공개 미러(int4)를 사용하고 Python 기준 벡터와의 코사인 골든 테스트(임계 0.93, 실측 최소 0.95)로 품질을 보증했다.
- **성향 압축의 재현율 부족(합성 F1 0.60, 일정 50%)**: 모델이 여러 사람이 나눠 말한 선호와 "토요일 불가" 같은 개인별 제약을 최종 결론으로 뭉뚱그린다. 선호 항목의 21%는 접두사만 있는 빈 항목이다. 대응: 압축 프롬프트에 참가자별 항목 분리 지시, 직렬화 단계에서 빈 항목 제거(10월).
- **Reflection 부정문 오탐**: "술집 대신 찻집"처럼 회피를 서술한 활동 설명이 불호 위반으로 판정돼 한 시나리오에서 재시도 3회를 소진(폴백 성공). 회피 표현 규칙 추가 검토.
- **PiiScrubber 이름 규칙 한계**: 호격 조사(아/야) 뒤 이름 미탐, 직함 호칭(교수님 등) 오탐, 명단에 없는 제3자 이름은 4%만 탐지. 단 실제 방어 대상인 Gemma 요약문 기준 누출은 359건 중 1건이었고 스크러버가 막았다. 규칙 보강은 호격 조사 추가와 직함 불용어 확대부터 진행.

### 3) 일정 문제

- 8월 방학 기간 개발 공백으로 출시 준비(서명·규칙 배포·정책)가 9월로 이월됐다. 대응: 9~10월에 출시 준비와 정량 평가를 병행하고, 기능 추가는 동결한다.
- 기말 보고서는 목차를 고정하고 파트 I(제안서)만 현행화된 상태다. 파트 II~IV는 10월에 코드 기준으로 현행화한다.
- 정량 평가의 사람 검토 항목(실제 대화 30건 정답 검토, 추천 위반 사람 채점 50회)이 남아 있다. 팀원 분담으로 9월 내 완료 예정.

### 4) 기타 문제

- 평가에 사용한 AI Hub 데이터는 재배포가 금지되어 대화 원문을 보고서·저장소에 실을 수 없다. 보고서에는 데이터셋 출처와 집계값만 싣고, 예시는 합성 대화로 대체한다.
- 개발 조직의 역할은 기술 스택 변경(Flutter → Kotlin/Compose) 이후 재배분되었으며, 팀원별 실제 담당 범위는 최종 보고서 제출 전 확정한다.
- 발표 시 주의할 표현: 새 모델을 학습·개발한 것이 아니고, 개인정보 유출 0을 보장하는 것도 아니다. "기존 모델을 사용하는 앱의 실행·검증·복구 로직을 구현했고, 실제 한국어 대화 데이터로 측정했다"가 정확한 주장이다.
