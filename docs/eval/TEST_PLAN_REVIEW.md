# 테스트 계획서 분석 및 확장안

작성일: 2026-09-13. 대상: 모이미 평가 계획(1~4단계)을 코드 실측과 데이터 실측에 대조한 결과.
원 계획서는 방향이 맞다. 다만 그대로 실행하면 막히는 지점이 세 곳 있고, 표본 규모가 발표 수치로 쓰기에 작다.

## 0. 결론

1. **데이터가 이미 익명화돼 있다.** AI Hub 한국어 대화 요약 데이터는 이름·전화·주소가 `#@이름#`, `#@전번#` 같은 토큰으로 치환돼 있다. 계획서의 "개인정보 미탐률"은 이 데이터를 그대로 넣으면 측정할 것이 없다. 해결은 합성 이름·번호를 토큰 자리에 주입하는 것이고, 주입한 값이 곧 정답이 되므로 오히려 정확한 지표가 나온다.
2. **지표 정의가 코드의 실제 출력과 어긋나는 항목이 있다.** 온디바이스 요약은 자유 산문이고, 날짜를 절대 날짜로 바꾸는 것은 Gemini 단계다. "날짜 추출 정확도"는 온디바이스와 클라우드 두 층으로 나눠 정의해야 한다. 성향 압축의 선호·불호는 문자열 정확 일치로 채점할 수 없다.
3. **실기기 결과를 파일로 남기는 실행기가 없다.** 현재 앱 로그는 화면 상태 목록이고 추천 시작 시 초기화된다(docs/evidence REVIEW.md 5절). 30건 대화를 돌려 수치를 내려면 결과를 JSONL로 쓰는 계측 테스트와 PC 측 채점 스크립트가 먼저 있어야 한다.
4. **양은 부족하다.** 데이터셋 30건은 2인 대화·짧은 대화 위주라 앱의 실제 입력(3~5인 단톡, 수십 메시지, 일정 변경)과 다르다. 데이터셋 30건 + 합성 20건, 후기 코퍼스 40건, 추천 시나리오 15건, PiiScrubber 단독 대량 검증(수천 건)으로 확장할 것을 제안한다.

## 1. 데이터 실측 (Validation ZIP)

| 항목 | 실측값 |
|---|---|
| 구성 | ZIP 1개 → 주제별 JSON 9개 (개인및관계, 미용과건강, 상거래, 시사교육, 식음료, 여가생활, 일과직업, 주거와생활, 행사) |
| 총 대화 수 | 35,004 |
| 참여자 수 | 2인 32,642 (93%), 3인 2,200, 4인 157, 5인 이상 5 |
| 발화 수 | 평균 11.3, 중앙값 10, 최대 30 |
| 라벨 | `body.summary` 1문장. 날짜·장소·목적 같은 구조화 정답은 **없다** |
| 발화 메타 | 발화별 `date`, `time` 있음 (2019~2020년). 상대 날짜("이번 토요일") 해석의 기준일로 쓸 수 있음 |
| 마스킹 토큰 | `#@이름#` 10,996회, `#@시스템#` 5,238, `#@이모티콘#` 3,219, `#@기타#` 1,937, `#@URL#` 434, `#@소속#` 250, `#@주소#` 144, `#@계정#` 78, `#@금융#` 56, `#@번호#` 32, `#@전번#` 24, `#@신원#` 9 |
| 모임 관련 후보 | 모임 키워드 4종 이상 + 발화 12개 이상: 69건. 3인 이상이면서 모임 키워드 3종 이상: 52건 |

레코드 구조:

```
header.dialogueInfo  { dialogueID, numberOfParticipants, numberOfUtterances, type, topic }
header.participantsInfo[] { participantID(P01..), gender, age, residentialProvince }
body.dialogue[] { utteranceID, turnID, participantID, date, time, utterance }
body.summary
```

계획서에 미치는 영향:

- 20~30건 선별은 가능하다. 다만 후보 69건 중 다수가 2인 대화라 "친구들 단톡"과는 거리가 있다. 3인 이상 52건을 우선 검토하고, 부족분은 2인 대화로 채운다.
- 모든 마스킹 토큰을 전처리해야 한다. `#@이름#`은 합성 이름으로 치환하고, `#@시스템#검색#`·`#@이모티콘#`·`#@URL#`은 삭제하거나 자연스러운 대체어로 바꾼다. 토큰을 그대로 두면 Gemma가 토큰을 그대로 옮겨 적거나 혼란스러워하는 결과가 섞여 지표가 오염된다.
- 발화 `date`를 `orchestrate(chatDate=)`에 넘겨야 상대 날짜 해석이 채점 가능하다. 단, 2019년 날짜로 기상청 API를 부르면 실패하므로 3단계 추천 시나리오는 현재 날짜 기준 합성 대화로 만든다.

## 2. 계획서 항목별 판정

### 1단계: 평가 기준과 데이터

| 계획 항목 | 판정 | 보완 |
|---|---|---|
| ZIP 구조 확인 | 완료 (위 표) | |
| 정답 항목 5종 (날짜, 장소, 목적, 선호·불호, 참여 가능 시간) | 적절 | 두 항목 추가: **PII 정답**(주입한 이름·번호·이메일 목록), **변경 이력**(일정·장소가 대화 중 바뀐 경우 최종값과 폐기값). 변경 이력이 없으면 2단계 4번 "일정 변경 처리"를 채점할 수 없다 |

### 2단계: 온디바이스 평가

계획서의 측정값을 실제 코드 출력에 대조한 결과다. 온디바이스 경로는 두 함수뿐이다. `summarizeForPrivacy`는 2~3문장 산문을 내고, `compressChatToStatus`는 participants·preferences·availability 세 배열을 낸다.

| 계획 측정값 | 실제 출력과의 대응 | 판정 | 채점 방식 제안 |
|---|---|---|---|
| 날짜 추출 정확도 | 요약문 안의 날짜 표현(산문) + availability 배열. 절대 날짜 변환은 Gemini가 함 | 두 층으로 분리 | 온디바이스: 요약문에 정답 날짜 표현 또는 정규화 동치("이번 주 일요일" ≒ "일요일")가 포함되는가. 클라우드: 3단계에서 `getWeather` 인자의 `date`가 `date_absolute`와 일치하는가 |
| 장소 추출 정확도 | 요약문 산문 | 가능 | 정답 장소 문자열 또는 상위 지역명 포함 여부 |
| 선호·불호 P/R | preferences 배열, `좋아요:`/`싫어요:` 접두사 | 정확 일치 불가 | 접두사 분리 후 **토큰 자카드 ≥ 0.5**를 일치로 간주하는 자동 채점 + 30건 사람 채점 병행. 극성(좋아요/싫어요) 뒤집힘은 별도 집계 |
| 핵심 정보 누락률 | 위 슬롯들의 재현율 | 가능 | 1 − 슬롯 재현율. 슬롯별로도 표기 |
| 개인정보 미탐률 | 요약문에 남은 주입 PII | **합성 주입 필수** | 두 값을 따로 낸다. (a) Gemma 요약 단독 누출률, (b) Gemma + PiiScrubber 통과 후 누출률. (b)가 방화벽 주장의 핵심 수치이고 (a)와의 차이가 스크러버의 기여다 |
| 정상 문장 오삭제율 | PiiScrubber 마스크 중 정답에 없는 것 | 가능 | `pii_decoys` 및 주입하지 않은 토큰이 `[이름]` 등으로 바뀐 비율 |
| 처리 시간 | 코드에 계측 없음 | 하네스에서 측정 | 요약·압축 각각 p50/p95. 모델 로드 시간은 분리. 기기명·백엔드(GPU) 명기 |
| 일정 변경·부정 표현·의견 충돌 | 데이터셋에 거의 없음 | 합성 필요 | 합성 20건에 배치. 주의: `mergeStatus`는 합집합 병합이라 변경 전 값이 남는 것이 **현재 설계**다. 이 테스트는 결함 발견이 아니라 알려진 한계의 수치화이며, 그대로 보고한다 |

추가로 측정할 가치가 있는 온디바이스 항목:

- **constrained 경로 성공률**: 압축이 툴콜 경로로 끝났는지 자유텍스트 폴백으로 갔는지. 폴백 비율이 곧 "깨진 JSON이 구조적으로 불가능"이라는 주장의 한계 수치다.
- **출력 형식 준수율**: 요약이 2~3문장인가, 마크다운 기호(`*`, `#`, `[`)가 없는가.
- **증분 병합 vs 일괄**: 실제 경로는 메시지 10개 델타마다 압축 후 병합이다. 50건 대화를 10개 청크로 나눠 병합한 결과와 일괄 압축 결과를 같은 정답으로 채점한다.
- **반복 안정성**: 같은 입력을 3회 돌려 요약·압축 결과가 얼마나 흔들리는지. Gemma 디코딩이 결정론적인지 실측이 없다.

### 3단계: 후기 검색과 추천 비교

| 계획 항목 | 코드 대응 | 판정 | 보완 |
|---|---|---|---|
| 후기 미사용 | 해당 구현 없음 | 쉬움 | `FeedbackRetriever` 포트에 빈 결과를 돌려주는 어댑터를 주입한다. 오케스트레이터 생성자 주입이라 앱 코드 변경 없이 테스트에서 조립 가능 |
| 키워드 검색 후기 | `KeywordFallbackRetriever` | 가능 | 테스트에서 직접 조립 |
| EmbeddingGemma 후기 | `EmbeddingGemmaRetriever` | 가능 | 모델 존재 시 기본 경로 |
| 후기 코퍼스 | **없음** | 필수 선행 | 후기 40건 합성(장소 유형·분위기·지역·부정 후기 혼합). 시나리오별 정답 후기 ID를 정해 top-1·top-3 적중률 채점. 기존 골든 테스트 문장 8건은 재사용 가능 |
| Reflection·Guardrail 없음 | `ReflectionService`는 object, `GuardrailService`는 final class라 주입 불가 | 코드 변경 없이 가능 | 1회차 프롬프트는 검증 피드백이 없는 기본 프롬프트와 동일하다. 따라서 **1회차 결과 = 검증 없음 조건, 최종 결과 = 검증 있음 조건**이다. `ReflectionEvaluated`·`GuardrailEvaluated` 이벤트가 시도별로 발행되므로 로그만 모으면 된다 |
| 조건 위반 추천 수 | Reflection 위반 수 + Guardrail CLOSED 수 | 가능 | 단, Reflection은 토큰 매칭이라 의미적 위반을 놓친다. 사람 채점으로 "실제 위반"을 따로 세어 자동 판정의 재현율도 보고한다 |
| 재시도 횟수 | `OrchestrationFinished.attempts` | 가능 | 폴백 성공(Reflection 미충족이나 장소 유효)은 성공과 구분해 집계 |
| 시나리오 10개 | 적절하나 적음 | 15개로 | 계획서 7유형에 추가: 후기가 현재 요청과 충돌(과거엔 좋았지만 이번엔 불호), 후기가 전혀 무관, 참가자 프로필 없음(null) |

3단계에서 반드시 정할 것:

- **Gemini 비결정성**: 시나리오당 조건별 3회 반복. 15 시나리오 × 3 검색조건 × 3회 = 135회 오케스트레이션. 시도 최대 3회이므로 Gemini 호출은 최대 약 400회, 도구 호출 별도. 프록시 백오프가 있으므로 실행 시간은 수 시간 단위로 잡는다.
- **로그인**: 프록시는 Firebase Auth 로그인 사용자만 통과한다. 테스트 기기가 로그인된 상태여야 한다.
- **기기 데이터 격리**: 기존 `RagE2ETest`는 시작 시 후기 전체를 삭제한다. 평가 실행기는 전용 roomId만 쓰고 `clearAll`을 호출하지 않는다. 임베딩 모델 파일도 이동하지 않는다.
- **Guardrail CLOSED의 의미**: 카카오 검색 0건이면 CLOSED다. "영업 여부"가 아니라 "검색 가능 여부"이므로 표에는 "장소 실존 검증"으로 쓴다.

### 4단계: 발표 자료

계획서의 결과표는 적절하다. 각 행에 **표본 수·조건·기기**를 붙이고, 처리 시간은 요약·압축·추천 세 값으로 나눈다. 아래 행을 추가한다.

| 추가 행 | 이유 |
|---|---|
| PII 누출률 (Gemma 단독 / 스크러버 후) | 방화벽이 실제로 무엇을 막았는지 보여주는 유일한 수치 |
| PiiScrubber 대량 검증 (n=수천) | 모델 없이 순수 Kotlin으로 돌릴 수 있어 가장 큰 표본을 얻는 항목 |
| constrained 경로 성공률 | 구조화 출력 주장의 근거 |
| 후기 검색 top-1: 키워드 vs 시맨틱 | RAG 도입 효과의 직접 비교 |
| 조건 위반: 1회차 vs 최종 | Reflection·Guardrail 효과 |

## 3. 개인정보·라이선스

- AI Hub 데이터는 이용 신청 승인 후 연구·교육 목적으로만 쓸 수 있고 재배포가 금지된다. 발표·보고서에는 데이터셋 이름과 출처를 표기하고, **대화 원문은 인용하지 않는다**. 예시가 필요하면 합성 대화를 쓴다.
- 선별 대화 원문이 담긴 평가 JSON은 `.eval-local/`에만 두고 git에 올리지 않는다. 이번에 `.gitignore`에 `.eval-local/`을 추가했다. 저장소에는 대화 ID 목록, 정답 스키마, 채점 스크립트, 집계 결과만 둔다.
- 데이터 자체는 이미 익명화돼 있어 실명은 없다. 주입하는 이름·번호는 실존 인물과 무관한 합성값만 쓴다.
- 추천 평가에서 Gemini로 나가는 것은 Gemma 요약문·프로필·후기뿐이어야 한다. 평가 실행기도 `orchestrate`를 그대로 타므로 원문이 경계를 넘지 않는다. 실행기가 결과 파일을 쓸 때도 원문은 기기 안 파일에만 남고 adb로 PC에 가져온다.

## 4. 필요한 도구 (계획서에 빠진 선행 작업)

| 산출물 | 위치 | 역할 |
|---|---|---|
| `build_evalset.py` | `scripts/eval/` | ZIP 읽기 → 후보 선별 → 마스킹 토큰 치환·PII 주입 → 평가 JSON 생성 (`.eval-local/evalset/`) |
| `OnDeviceEvalRunner` | `app/src/androidTest/.../eval/` | 평가 JSON을 모델 폴더에서 읽어(골든 테스트 전례) 대화마다 요약·압축·스크러버 실행, 소요 시간과 함께 `eval_ondevice.jsonl`로 기록. 판정은 하지 않고 파일이 없으면 `assumeTrue`로 스킵 |
| `score_ondevice.py` | `scripts/eval/` | JSONL + 정답 → 슬롯 재현율, 선호 P/R/F1, PII 누출률, 오탐률, 시간 분포 |
| `PiiScrubberBulkTest` | `app/src/test/` | 데이터셋 수천 건에 합성 PII 주입 후 순수 Kotlin으로 정밀도·재현율 산출. JVM에서 분 단위로 끝남 |
| `RecommendationEvalRunner` | `app/src/androidTest/.../eval/` | 시나리오 × 검색 조건 × 반복 → `AgentEvent` 전체를 `eval_recommend.jsonl`로 기록 |
| `score_recommend.py` | `scripts/eval/` | 검색 top-k 적중, 1회차 vs 최종 위반 수, 재시도·폴백·실패 비율, 날짜 절대값 일치 |
| 사람 검토 시트 | `.eval-local/review.csv` | 정답 검토와 위반 사람 채점 |

기기·모델 상태: SM-F966N 1대가 adb에 연결돼 있고 Gemma·EmbeddingGemma 모델은 준비돼 있다. Python `sentence-transformers`도 설치돼 있어 검색 골든 확장이 가능하다.

## 5. 확장 후 최종 규모

표본 규모는 "정답을 사람이 달아야 하는가"로 나눈다. 정답이 불필요한 지표는 실행 비용만 들므로 수백~수천 건으로 올리고, 정답이 필요한 지표는 반자동 초안 + 사람 검증과 합성 비중 확대로 100건까지 올린다. 모든 표에 n과 95% 신뢰구간(Wilson)을 함께 적는다. n=50이면 ±14%p, n=100이면 ±10%p 수준이다.

**정답 불필요 축 (자동 채점, 대량)**

| 지표 | 정답 출처 | 규모 | 생성 상태 |
|---|---|---|---|
| PII 누출률 (Gemma 단독 / 스크러버 후) | 주입한 합성값 | 대화 315건 (주제 층화, 전화 100·이메일 57 추가 주입) | `bulk_ondevice.json` 생성됨 |
| PiiScrubber 단독 정밀도·재현율 | 주입값 | 대화 5,000건 (이름 1,570회, 전화 1,499, 이메일 766) | `scrubber_bulk.jsonl` 생성됨, `PiiScrubberBulkEvalTest` |
| 출력 형식 준수, constrained 성공률, 처리 시간 p50/p95 | 규칙 | 위 315건에 얹힘 | 실행기 필요 |
| 요약 핵심 정보 보존 (거친 지표) | 데이터셋 `summary` 명사 포함률 | 위 315건 | 채점 스크립트 필요 |
| 후기 검색 키워드 vs 시맨틱 top-1 | 후기 40건 × 유사 질의 5개, 원본 후기가 정답 | 질의 200건 | 후기 코퍼스 필요 |

**정답 필요 축 (사람 검증, 제한 규모)**

| 지표 | 규모 | 정답 생성 방법 |
|---|---|---|
| 슬롯 추출(날짜·장소·목적·선호·일정) | 100건 = 실제 30 + 합성 70 | 후보 120건(`candidates_review.md`)에서 30건 선택. 합성은 작성 시 정답 동봉. 발표에서 실제·합성 구분 표기 |
| 추천 시나리오 | 30건 × 조건 3 × 반복 3 = 270회 | 자동 판정(Reflection·Guardrail 이벤트)은 전량 집계 |
| 조건 위반 사람 채점 | 무작위 표본 50회 | 자동 판정의 재현율 추정용 |

주의: 데이터셋 원문을 Gemini 등 외부 LLM에 보내 정답 초안을 만드는 방식은 쓰지 않는다. AI Hub 약관상 제3자 서비스 전송이 재배포로 해석될 여지가 있다. 초안은 로컬 규칙(요일·날짜 정규식, 지명 사전)과 사람으로만 만든다.

## 6. 실행 순서

1. `build_evalset.py`로 후보 69건을 뽑아 사용자가 30건을 고르고 정답을 채운다. 동시에 합성 20건을 작성한다.
2. `PiiScrubberBulkTest`를 먼저 돌린다. 모델이 필요 없어 당일 수치가 나온다.
3. `OnDeviceEvalRunner`를 실기기에서 돌리고 `score_ondevice.py`로 채점한다.
4. 후기 코퍼스 40건과 시나리오 15건을 작성하고 `RecommendationEvalRunner`를 돌린다.
5. 집계표를 `docs/evidence/<날짜>/`에 남기고 DEVLOG에 결정 사항을 기록한다.
